# 后端项目分析报告

> 基于对 `oa-system` 后端源码的完整阅读（配置 / 安全 / Controller / Service / Entity / DTO / VO / 枚举 / SQL 脚本 / MQ 链路）。
> 结论：本报告用于指导前端设计与接口对接，**不改动后端代码**。

---

## 1. 技术栈与架构总览

| 维度 | 说明 |
|---|---|
| 框架 | Spring Boot **4.1.0**（WebMVC），Java 17 目标 / JDK 21 运行 |
| ORM | MyBatis-Plus 3.5.16（分页插件 + 逻辑删除 + 公共字段自动填充） |
| 数据库 | MySQL 8（库名 `oa_system`），脚本在 `src/main/resources/db/` |
| 安全 | Spring Security 7 + JWT（jjwt 0.12.6，HS256），无状态（STATELESS） |
| 缓存 | Redis（登录态 / 用户权限 / 用户详情 / 菜单树） |
| 消息 | RabbitMQ（审批结果异步通知） |
| 接口文档 | springdoc-openapi 3.0.3 → Swagger UI：`http://localhost:8080/swagger-ui.html` |
| 端口 | 8080 |
| 打包 | 项目自带 `.\mvnw.cmd` |

### 分层结构
`controller`（仅收参返参）→ `service/impl`（业务）→ `mapper`（数据访问）→ `entity`/`dto`/`vo`。公共返回与异常见下。

### 统一返回格式 `Result<T>`
```json
{ "code": 200, "message": "success", "data": { } }
```
分页接口返回 `Result<PageResult<T>>`：
```json
{
  "code": 200, "message": "success",
  "data": { "total": 35, "records": [ ... ], "pageNum": 1, "pageSize": 10 }
}
```

### 错误码 / HTTP 状态映射（`GlobalExceptionHandler` + 安全处理器）
| 场景 | HTTP | body.code | body.message |
|---|---|---|---|
| 成功 | 200 | 200 | success |
| 业务异常（如状态非法） | 400 | 400 | 具体提示 |
| 参数校验失败 | 400 | 400 | `字段: 提示` |
| 未认证 / token 失效 / 已登出 | 401 | 401 | 未认证或登录已过期 |
| 无权限（方法级 `@PreAuthorize` 或业务内校验） | 403 | 403 | 无访问权限 |
| 资源不存在 | 404 | 404 | 资源不存在 |
| 系统异常 | 500 | 500 | 系统内部错误 |

> 注意：部分业务异常（`BusinessException` 携带的 code 不在 400/401/403/404 中）HTTP 状态码为 200，但 body.code 仍为业务码。**前端必须统一按 `body.code` 判断成功，不能只依赖 HTTP 状态。**

### 认证方式
- 请求头：`Authorization: Bearer <token>`
- token 有效期 30 天（`expiresIn` 秒）；登录后写入 Redis 登录态，登出/被踢后 token 立即失效。
- 未带 token / token 无效 / 已登出 → 401；已认证但无权限 → 403。

### 公共字段约定
- 所有业务表含 `create_time`、`update_time`（格式 `yyyy-MM-dd HH:mm:ss`）、`deleted`（逻辑删除）。
- 日期字段 `LocalDate` 格式 `yyyy-MM-dd`；时间 `LocalDateTime` 格式 `yyyy-MM-dd HH:mm:ss`。
- 布尔/状态用整数（TINYINT），金额 `DECIMAL`。

## 3. 核心业务流

### 3.1 认证流
```
注册（公开）→ 登录（签发 JWT + 缓存登录态/用户权限）→ 携带 token 访问 → 
JWT 过滤器校验 Redis 登录态 + 加载用户权限 → 鉴权放行 → 登出删缓存（token 立即失效）
```

### 3.2 审批流（请假/报销，单级审批）
```
申请人提交（指定 approverId，落「提交」记录）→ 状态 DRAFT→PENDING
→ 审批人 通过/拒绝（落记录 + MQ 异步通知申请人）→ PENDING→APPROVED/REJECTED
→ 申请人可在 DRAFT/PENDING 撤回 → CANCELLED
```
状态机（非法流转返回 400）：
```
0草稿 → 1待审批 → 2通过 / 3拒绝；0/1 可撤回 → 4撤回
```
审批记录动作：1提交 / 2通过 / 3拒绝 / 4撤回。

### 3.3 RBAC 权限聚合
```
用户 → sys_user_role → 角色(启用) → sys_role_menu → 菜单(启用且 perms 非空) → 权限标识集合
角色编码以 ROLE_ 前缀进 Spring Security；权限标识原样（hasAuthority）。
```
`/api/auth/me` 返回：`user`（UserVO）+ `roles`（角色编码数组）+ `permissions`（权限标识集合）。

### 3.4 文件流
```
上传（multipart 字段 file，≤10MB，扩展名白名单 jpg/jpeg/png/gif/pdf/doc/docx/xls/xlsx/txt/csv）
→ 本地磁盘 ./upload/yyyyMMdd/uuid.ext → 落 file_info → 返回 FileVO（含下载 url）
下载：GET /api/files/{id}/download（二进制流，按原始文件名）→ 删除（逻辑删 + 物理删，仅上传者或 admin）
```

### 3.5 通知流
```
审批通过/拒绝 → 发送 MQ(oa.approval.exchange → oa.approval.notice.queue)
→ 消费者写 sys_message（接收人=申请人，type=APPROVAL）→ 前端未读数/列表
```

## 5. ⚠️ 前端对接必须注意的设计问题 / 后端缺口

以下为本次分析发现的、影响前端实现的要点（**不修改后端**，前端采用规避方案；如需后端补齐，请另立阶段确认）：

1. **缺少「当前用户菜单树」接口**。`/api/auth/me` 只返回权限标识集合；`/api/menus/tree` 需 `system:menu:list` 权限且返回全量菜单。
   → 前端方案：用**静态路由表 + permissions 过滤**生成侧边栏菜单和动态路由，或后端后续补充 `GET /api/auth/menus`。

2. **注册用户无默认角色**。`/api/auth/register` 创建的用户没有任何角色，登录后访问任何 RBAC 接口均 403、看不到系统管理菜单。
   → 前端方案：注册成功页提示「等待管理员分配角色」。

3. **普通用户无法查询用户列表 → 无法选择审批人**。提交请假/报销需 `approverId`，但查询用户列表 `/api/users` 需要 `system:user:list` 权限。
   → 前端方案（二选一，需你确认）：
   - A. 后端补一个免权限的「启用用户简表」接口（推荐，改动小）；
   - B. 前端提交表单的审批人改为「输入 userId」或隐藏为固定值（体验差）。
   **这是当前最大的体验断点，建议后续补后端接口。**

4. **无「新建用户」的管理员接口**。用户管理页「新增用户」只能走公开的 `/api/auth/register`（自带校验：用户名 3-20、密码 8-20 且含字母数字）。
   → 前端方案：新增用户调用 register + 再调用分配角色接口。注册接口会返回密码校验错误，前端表单需对齐规则。

5. **文件下载是二进制流，且 `url` 为相对路径**（`/api/files/{id}/download`）。浏览器 `<a href>` 无法带 Authorization 头。
   → 前端方案：下载用 axios `responseType: 'blob'` 或带 token 的 fetch，再用 Blob URL 触发下载；或下载接口本身可考虑用 query 参数 token（不推荐，仅说明）。

6. **审批 通过/拒绝 接口的请求体可选**（`@RequestBody(required=false)`）。前端调用统一发 `{}` 或 `{"comment":"..."}`，避免空 body 触发 400。

7. **`/api/cache/evict` 无权限控制**，任何登录用户可清缓存（运维性质）。前端不应在业务菜单中暴露该入口。

8. **分页参数默认值不统一**：`UserQuery`/`RoleQuery` 在 DTO 无默认值时由 Service 兜底（pageNum<1→1，pageSize<1→10，上限 100）。前端所有分页请求**统一显式传 `pageNum` / `pageSize`**。

9. **通知内容硬编码「审批人ID：xxx」而非姓名**（消费端拼接），展示体验一般；前端可原样展示或自行美化。

10. **无数据统计接口**（prompt 原始需求含「数据统计」，后端未实现）。仪表盘若无真实数据接口，建议暂缓或用静态占位。

11. **`/api/approvals/records` 未做「仅申请人/审批人」校验**，参数（businessType + businessId）可枚举；属后端权限边界，前端需在详情页自行控制入口。

## 7. 需要状态管理（Pinia）的数据

| Store | 内容 | 说明 |
|---|---|---|
| `useUserStore` | token / userInfo（user、roles、permissions）/ 登录登出 / 刷新 me | 全局持久化 token（localStorage），会话内缓存用户信息 |
| `usePermissionStore` | 静态路由表 / 按 permissions 过滤后的动态路由 / 侧边栏菜单 | 登录后生成，刷新时重建 |
| `useAppStore`（可选） | 侧边栏折叠 / 标签页 | 布局 UI 状态 |

审批、文件、消息列表为页面级局部状态（`ref`/`reactive` + 组件内请求），**不建议**放 Pinia（数据量大且页面独立）。
